# План исправлений по аудиту Textual TUI

Дата аудита: 2026-10-03.

Документ фиксирует результаты статического аудита проекта **IDvjPy_term** по четырём направлениям:

- отсутствие блокировок Textual event loop;
- корректное использование механизмов Textual;
- безопасность секретов, истории и буфера обмена;
- чистота и поддерживаемость кода.

Код в рамках аудита не менялся. План нужно выполнять небольшими изолированными шагами с целевыми тестами.

## Краткая оценка

### Сильные стороны

- Долгие shell-команды, `kubectl`, LLM, HTTP-import, конвертация документов и `rg` преимущественно вынесены из UI-потока.
- Возврат из рабочих потоков обычно проходит через `call_from_thread`, а не через прямое изменение виджетов.
- Есть защита секретов: заморозка маскированного вывода (`freeze_secrets`), очистка session secret-файла, таймер очистки буфера, vault auto-lock и остановка групп дочерних процессов.
- Логика разнесена по специализированным модулям: `vault`, `clipboard`, `md_convert`, `remote_source`, `db_transfer`, `shell_env`.
- Внешние команды, не требующие интерактива, получают `stdin=subprocess.DEVNULL`; timeout завершает группу процесса.
- Заставка уже ограничивает частоту рендера и не перерисовывает неизменившийся canvas.

### Основные риски

- `src/app.py` содержит слишком много ролей и вырос примерно до 13 тысяч строк.
- Часть файловых операций, SQLite-запросов и clipboard subprocess-вызовов выполняется в обработчиках UI.
- В проекте одновременно применяются ручные `threading.Thread`, Textual workers и timers без единого lifecycle-слоя.
- Широкие `except Exception` местами скрывают ошибки данных и логики.

## Critical — исправить в первую очередь

### C1. Убрать системный clipboard I/O из event loop

**Затронутые файлы:** `src/clipboard.py`, `src/app.py`.

`copy_text_to_clipboards()` и `paste_text_from_clipboards()` синхронно вызывают `pyperclip` и несколько внешних программ (`xclip`, `xsel`, `wl-copy`, `wl-paste`). У каждого `subprocess.run()` есть timeout `0.4` секунды. Это вызывается из обработчиков клавиш и мыши (`Ctrl+V`, `Ctrl+C`, right-click, F3, vault copy), поэтому при недоступном backend UI может заметно подвисать.

**План:**

1. Оставить немедленное обновление внутреннего clipboard Textual, если оно доступно.
2. Системные backend-вызовы выполнять в worker/thread.
3. Возвращать итоговую индикацию в UI через `call_from_thread` или Textual worker callback.
4. Ограничить число попыток backend-ов и сохранить короткий timeout.
5. Для vault перед очисткой по возможности проверить, что clipboard ещё содержит значение vault, а не новый текст пользователя.

**Тесты:**

- вставка/копирование не блокирует UI при timeout backend-а;
- right-click вставляет результат worker-а в исходную cursor position;
- `:key cp` очищает только ожидаемое значение;
- ошибки clipboard backend-а не ломают internal clipboard fallback.

### C2. Сделать `:md` безопасным для больших и специальных файлов

**Затронутый файл:** `src/app.py`, `_open_md_file()`.

Сейчас `path.read_bytes()` читает файл целиком в UI event loop до определения его типа. Большой PDF, лог, FIFO или файл на медленном/NFS mount способен зависнуть или привести к чрезмерному потреблению памяти.

**План:**

1. До полного чтения проверять тип файла и размер через `stat()`.
2. Читать небольшой префикс для определения текстового/бинарного формата.
3. Перенести полное чтение, декодирование и конвертацию в worker.
4. Ввести настраиваемый лимит предварительного чтения и понятное сообщение для слишком больших файлов.
5. Для plain text использовать streaming/ленивый viewer или явный preview вместо обязательной загрузки целиком.
6. Отдельно обрабатывать FIFO, device-файлы и недоступные пути.

**Тесты:**

- слишком большой файл не читается полностью в UI handler;
- FIFO и directory дают понятную ошибку;
- worker возвращает результат после отмены/ошибки без обращения к закрытому event loop;
- обычный Markdown и document conversion сохраняют текущую навигацию к строке.

### C3. Вынести `:w` из UI-потока

**Затронутый файл:** `src/app.py`, `_handle_write_command()`.

`:w` собирает весь журнал, обрабатывает форматирование, формирует большую строку и пишет её синхронно. На большом журнале или медленном filesystem интерфейс блокируется.

**План:**

1. В UI снять только маскированный snapshot блоков в правильном порядке.
2. Сериализацию и запись выполнять в worker.
3. Для больших объёмов писать файл порциями.
4. Явно зафиксировать append-поведение `:w` в help; при необходимости добавить отдельный режим overwrite.
5. Исключить запись raw stdout/stderr и хранить в export только frozen/masked display text.

**Тесты:**

- `:w` не содержит `$$` и vault-значений;
- большой journal не выполняет файловую запись в handler;
- ошибка записи возвращается в journal;
- повторный `:w` имеет документированную append-семантику.

### C4. Ограничить и вынести completion / SQLite I/O

**Затронутый файл:** `src/app.py`.

Completion выполняет синхронные `os.listdir()` и SQLite-вызовы при вводе. Особенно опасны большие каталоги, сетевые mount-ы и fallback, который перебирает родительские директории.

**План:**

1. Добавить debounce для file/tag completion.
2. Кэшировать результаты по `cwd`, prefix и filesystem metadata.
3. Ограничивать число кандидатов до сортировки/форматирования.
4. Вынести filesystem scan и тяжёлые DB-запросы в cancellable worker.
5. Игнорировать устаревший результат, если текст input уже изменился.
6. Не использовать ошибки filesystem как причину повторять неограниченный обход каталогов.

**Тесты:**

- completion не блокирует UI на медленном `listdir`;
- устаревший worker-результат не подменяет новый prefix;
- список кандидатов ограничен;
- fallback к родительской директории прекращается детерминированно.

**Статус.** Реализовано ограничение и кэш: `os.scandir` без `stat` на запись,
кэш листинга по `(каталог, mtime_ns)`, предел сканирования
(`FILE_COMPLETION_SCAN_LIMIT`) и ограниченный по глубине fallback
(`FILE_COMPLETION_PROBE_DEPTH`); кэш библиотеки БД уже не перечитывает SQL на
каждое нажатие. Полный перенос сканирования в отменяемый worker, debounce,
отбрасывание устаревшего результата и признак «список обрезан» в UI переносятся
в **S2** (общий wrapper фоновых задач) — они меняют синхронный контракт
`get_input_completion_items`, которым пользуются тесты и внешние вызовы.

## Suggestions — улучшения следующего уровня

### S1. Декомпозировать `CommandRunner`

**Затронутый файл:** `src/app.py`.

`CommandRunner` объединяет UI, командный роутинг, процессы, TTY, vault, history, SQLite, import/export, LLM, K8s и settings.

**Предлагаемые границы:**

| Компонент | Ответственность |
| --- | --- |
| `CommandRunner` | Textual UI, routing, отображение сообщений и виджетов |
| `CommandExecutor` | shell-процессы, process registry, timeout, kill |
| `SessionState` | env, `$$` secrets, vault state, scope, history state |
| `CommandService` | исполнение `:`-команд без прямого доступа к виджетам |
| `CompletionService` | tags/files/history completion, cache и отмена запросов |
| `JournalService` | snapshot, search, export, output persistence |
| `SettingsRepository` | чтение, валидация и запись конфигурации |

Переносить по одному вертикальному срезу с сохранением существующих публичных методов и тестов.

### S2. Унифицировать background jobs через Textual Workers

Сейчас используются `threading.Thread`, `run_worker` и timers. Это усложняет остановку, обработку ошибок и защиту от callback после закрытия event loop.

**План:**

1. Для новых работ использовать `run_worker(..., thread=True, group=..., exclusive=...)` или `@work(thread=True)`.
2. Сделать единый wrapper для start/status/error/cancel callback.
3. Оставить ручные потоки только для мест, где это обосновано, и документировать lifecycle.
4. Во всех callback после worker-а проверять, что app/screen ещё активны.

### S3. Сузить широкие `except Exception`

Широкие перехваты допустимы при cleanup и best-effort UI. В сервисах данных они скрывают реальные ошибки.

**План:**

1. Заменять на ожидаемые исключения (`OSError`, `JSONDecodeError`, database errors, `NoMatches`, markup errors).
2. Для best-effort UI fallback оставить broad catch, но добавить debug logging.
3. Не допускать silent broad catch на пути записи данных, секретов или migration.
4. Включить соответствующее правило Ruff при отсутствии чрезмерного шума.

### S4. Уменьшить время удержания пароля в `VaultSecretScreen`

**Затронутый файл:** `src/vault_prompt.py`.

Первое значение password confirm хранится в `self._first` до закрытия модалки. Python не может надёжно очистить immutable `str` из памяти, но можно не удерживать лишнюю ссылку.

**План:**

1. В `action_cancel()` обнулять `self._first`.
2. Обнулять ссылку после успешного `dismiss()`.
3. Не создавать лишних копий secret/password.
4. Добавить тесты cancel, mismatch и success.

### S5. Зафиксировать инвариант маскирования для `:w`

`CommandBlock` хранит raw output для pipe, `$OUT`, F3 и `:cmd`, а показанный текст маскируется/замораживается. Нужно доказать тестом, что `:w` экспортирует только masked output.

**План:**

1. Создать secret через `$$NAME=value`.
2. Выполнить команду, которая печатает `value`.
3. Экспортировать журнал через `:w`.
4. Убедиться, что `value` отсутствует в файле.
5. Отдельно проверить разрешённые явные исключения: F3, `:log`, `:cmd`.

### S6. Разгрузить `on_mount()`

`on_mount()` выполняет settings I/O, YAML parsing, SQLite init, cache loading, migration и provisioning синхронно.

**План:**

1. Оставить синхронно только минимальный UI bootstrap.
2. Разнести инициализацию на короткие стадии: settings → DB → cache → migrations → startup checks.
3. Долгие стадии запускать worker-ами с кратким status сообщением.
4. Не показывать UI как готовый до инициализации критичной DB-state.

### S7. Использовать Reactive и Message точечно для глобального UI state

Сейчас состояние меняется преимущественно прямыми присваиваниями и callback-ами. Полная миграция не нужна, но состояние крупного приложения должно быть явнее.

**Подход:**

- reactive для subtitle/status, active process count, vault state, demo/runbook/watch state;
- собственные сообщения для результатов: `CommandCompleted`, `RemoteImportReady`, `ConversionFinished`;
- локальные widget-обновления оставить прямыми там, где состояние не глобальное.

### S8. Проверить импорт окружения после TTY на пересечение с секретами

**Затронутые файлы:** `src/shell_env.py`, TTY ingest в `src/app.py`.

Нужно явно исключать имена и значения известных `$$`/vault секретов из child shell environment dump. Иначе возможна рассинхронизация между `local_env`, `os.environ`, маскированием и vault lifecycle.

**Тесты:**

- дочерний dump содержит существующий `$$`-secret;
- дочерний dump содержит vault env value;
- оба значения не попадают в history/journal и не заменяют внутреннее secret state.

### S9. Документировать поверхность clipboard для vault

`:key cp` копирует секрет сразу в несколько каналов: Textual clipboard, OSC 52, pyperclip, CLIPBOARD и PRIMARY. Это обеспечивает совместимость, но увеличивает поверхность утечки.

**План:**

1. Явно описать это в `:? key` и README.
2. Рассмотреть настройку набора clipboard backend-ов для vault.
3. Рассмотреть режим только Textual/OSC 52 для окружений с повышенными требованиями.
4. Сохранять текущую очистку по TTL и выходу из TTY, но не обещать гарантированную очистку внешнего clipboard manager-а.

### S10. Добавить отдельные CI jobs для lint и type checking

На машине аудита `ruff` не был установлен. `compileall` прошёл без syntax errors, но `python3 -m ruff check src tests` завершился ошибкой `No module named ruff`.

**План:**

1. Добавить/сохранить `ruff` и `basedpyright` в `requirements-dev.txt`.
2. В GitHub Actions добавить короткие jobs `lint` и `types`.
3. Не связывать lint/type-check с долгим полным pytest.
4. Для локальной проверки использовать:

```bash
python3 -m pip install -r requirements-dev.txt
python3 -m ruff check src tests
python3 -m basedpyright
```

### S11. Управлять внешними интерактивными сессиями через `tmux`

**Цель.** Открывать полноценные интерактивные команды (`ssh`, shell контейнера,
`kubectl exec -it`, `tail -f`) в новом окне или вкладке терминала и затем
направлять им команды из основного экземпляра IDvjPy. Не встраивать эмулятор
терминала в Textual и не заменять настоящий TTY.

**Почему `tmux`.** Окно, открытое через `:term` / `&`, нельзя надёжно снова
найти и записать в его stdin. `tmux` даёт настоящий PTY, стабильное имя
сессии, проверку состояния, отправку клавиш и снимок видимой области. Это
сохраняет нативную работу ssh, MFA, ssh-agent, Tab, Ctrl+C, `vim`, `less`,
`htop` и изменение размера терминала.

#### Контракт и UX

Новая группа команд, не смешиваемая с `:send`:

```text
:term start NAME -- COMMAND
:term send NAME COMMAND
:term status [NAME]
:term attach NAME
:term capture NAME
:term stop NAME
```

Примеры:

```text
:term start prod -- ssh prod
:term send prod "hostname; uptime"
:term send prod "cd /srv/app && git status"
:term capture prod
:term attach prod
:term stop prod
```

- `start` открывает новый терминал в текущем режиме `term_open` (window/tab)
  и запускает именованную локальную tmux-сессию:
  `tmux new-session -A -s <internal-name> -- <command>`.
- `send` передаёт текст через `tmux send-keys … Enter`. Это ввод активной
  pane, а не отдельное исполнение shell-команды.
- `capture` использует `tmux capture-pane -p` и добавляет снимок экрана
  отдельным блоком журнала. Это не поток stdout и не заменяет вывод в
  терминальном окне.
- `attach` открывает новое окно/вкладку с `tmux attach-session`.
- `stop` сначала требует явного подтверждения, затем завершает только
  управляемую IDvjPy tmux-сессию.
- Обычные `:term`, `:term --tab`, `:term --window`, `& cmd` и `> cmd`
  остаются без изменений.

#### Границы поведения

- `send` безопасен для shell-приглашения и линейных команд. Если в pane
  открыт `vim`, `less`, `htop`, парольный prompt или мастер установки,
  текст попадёт именно активной программе. IDvjPy не пытается угадать,
  ожидает ли shell команду.
- Вывод остаётся в окне/вкладке терминала. В журнал попадает только явный
  `capture`, уже обработанный действующими правилами отображения.
- Не реализовывать собственный PTY/ANSI-эмулятор и не делать «ssh внутри
  Textual»: это отдельная сложная подсистема и ухудшит проверенный путь
  `> ssh`.
- Сессии локальны для экземпляра IDvjPy; они не заменяют `:send`, который
  передаёт команды между экземплярами через inbox.

#### Секреты

- В `:term send` запрещать раскрытие живых `$$` и значений vault: секрет
  нельзя передавать как текст в tmux, потому что он попадёт в scrollback,
  историю удалённого shell или журнал терминала.
- `:key use` / `:key exec` допустимы только при старте сессии, когда
  значение передаётся через env дочернего процесса, а не argv.
- В metadata-файле и журнале хранить только маскированную команду и
  несекретные атрибуты.

#### Хранение состояния

- Добавить в data directory файл `term_sessions_<instance>.json` с
  несекретными метаданными: пользовательское имя, внутреннее tmux-имя,
  команда для отображения, время создания и режим открытия.
- Внутреннее имя namespaced, например `idvjpy-<instance>-<name>`, с
  безопасной нормализацией имени.
- `status`, `send`, `attach`, `capture` перед работой проверяют сессию
  через `tmux has-session -t`; устаревшую запись удаляют только после
  подтверждённого отсутствия tmux-сессии.
- Не удалять и не захватывать пользовательские tmux-сессии, которые не
  были созданы IDvjPy.

#### Реализация

1. Создать `src/term_sessions.py`: dataclass metadata, валидация `NAME`,
   load/save с правами `0600`, построение argv для `tmux`, `has_session`,
   `send_keys`, `capture_pane`, `kill_session` и понятная подсказка при
   отсутствии `tmux`.
2. Расширить текущий обработчик `:term` в `src/app.py`, сохранив
   `--tab` / `--window`: routing `start/send/status/attach/capture/stop`,
   подтверждение перед `stop` и запуск через существующий
   `open_terminal_command`.
3. Добавить UI-строки в `src/locales/en.yml`; русский/китайский — по
   необходимости. Дополнить `:? term`, README и COMPACT_SUMMARY примерами
   и ограничениями.
4. Добавить учебный seed-пример реальных `tmux` + ssh:
   `ssh prod -t 'tmux new-session -A -s operations'`; запускать только
   через `>`, не через автоматический demo.

#### Тесты

- Unit-тесты `term_sessions.py`: валидация имён, namespace, JSON,
  права файла, argv, маскирование.
- Mock `subprocess.run`/`Popen`: отсутствие tmux, stale-session,
  `has-session`, send/capture/stop и ошибки процессов.
- Routing-тесты `:term start`, `send`, `status`, `attach`, `capture`,
  `stop`; существующие `:term --tab` и `:term --window` не регрессируют.
- Отрицательные тесты секретов: живые `$$`/vault-значения не входят в
  `send`, metadata, историю, блоки и аргументы tmux.
- Тесты подтверждения: `stop` не выполняется без явного Enter.

## Порядок реализации

1. **C1:** clipboard вне event loop.
2. **C2:** безопасное асинхронное чтение в `:md`.
3. **C3:** worker для `:w` и тест маскирования.
4. **C4:** completion cache/debounce/worker.
5. **S2:** общий background-job wrapper и постепенная миграция ручных потоков.
6. **S6/S7:** lifecycle и UI state.
7. **S1:** постепенное выделение сервисов из `CommandRunner`.
8. **S11:** внешний настоящий TTY через именованные tmux-сессии; не менять `> cmd` и `:send`.
9. **S3–S5/S8–S10:** целевые hardening, тесты и CI.

## Правила выполнения
