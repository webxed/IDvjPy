[bold]Vault — password-encrypted secret store (`:key`)[/bold]

  A long-lived store of secrets, unlike `$$NAME=…` (that one lives only for the
  session). The file is `vault.json.enc` in the data dir (0600): its header is
  public, the entries are encrypted (scrypt + AES-256-GCM). A wrong password or a
  damaged file gives an explicit error, not garbage on screen.

  Unlock once per session; the password then stays in memory only:

    :key init               create the vault (password asked twice)
    :key unlock | lock      unlock for this session / forget it
    :key                    file, lock state, the names (never the values)

  Managing entries:

    :key add NAME [hint]    add or replace a value; the window also has a comment
    :key comment NAME [text]  change the comment alone (the value is kept);
                              `;` separates links, no text shows it, `-` clears it
    :key gen NAME [len]     generate a random value
    :key list               names and comments (each link on its own line)
    :key find TEXT          search by name and comment, case-insensitive (alias
                              `search`); values are never searched or shown
    :key rm NAME            remove an entry

  Getting a value out — a value is never printed:

    :key cp NAME               → clipboard (cleared on TTY exit, and in 60 s)
    :key use NAME [VAR]        → $VAR in this session's environment
    :key exec NAME[=VAR] -- cmd    $VAR in the child env, not in argv
    :key stdin NAME -- cmd         feed the value to the command's stdin
    :key unuse [NAME|*]            remove exported variables (NAME, or `*` for all)

  `exec` guesses the variable for known programs (sshpass → SSHPASS,
  psql → PGPASSWORD, mysql/mysqldump → MYSQL_PWD, vault → VAULT_TOKEN, restic,
  borg, redis-cli); for anything else say `NAME=VAR` explicitly. The program
  itself must be installed (`apt install sshpass` and the like) — the vault only
  supplies the variable. For sshpass use `-e` (it reads `$SSHPASS`), never `-p`:
  `-p` puts the value into argv, where `ps` can see it.

  Comments are a note per entry — where the key belongs, links, a reminder:
  `:key comment SSH_PROD prod ssh;https://gitlab.example/proj;ssh://u@host`.
  They are **not** secrets and are not masked: they go into the journal, `↑` and
  `history_*.txt` as typed — never paste the value itself (or a URL with a token)
  into a comment. The comment is shown next to the value in `cp`/`use` messages.

  Rules: values never enter the journal, `:o`, `↑`, `history_*.txt`, `:send` or
  `:export`; while the vault is unlocked they are masked like `$$`-secrets, and
  variables exported with `use` stay masked too (even after the vault locks). `cp`
  is the weakest link — other programs can read the clipboard. The `cryptography`
  package is required (`pip install cryptography`); without it the rest of the
  app keeps working.

  [bold]TOTP codes:[/bold] two-factor codes without a phone app. The secret is kept
  encrypted like any other entry; only the current one-time code reaches the
  screen, so the secret itself is never printed:

    :key add GITHUB --totp      paste a base32 secret or an otpauth:// link
    :key totp GITHUB            live code: updates every second, Enter/`c` copies
                                  the fresh code, Esc closes without copying

  The `--totp` value takes a bare base32 key (`jbsw y3dp ehpk 3pxp`) or a link from
  a QR code (`otpauth://totp/Issuer:acct?secret=…&issuer=…&digits=…`): digits
  (6–8), period and algorithm (SHA1/256/512) are stored per entry. The code is
  **not** a secret — it can be shown and copied (it lives 30 s and may land in the
  journal / `:o`, unlike the secret). The counter comes from the system clock, so
  a wrong clock gives wrong codes. Both factors end up in one store here — handy
  for keeping codes around, but not a reason to trust a borrowed password.

  [bold]Auto-lock:[/bold] the store locks itself after `vault_idle_lock` minutes
  with no vault operation (15 by default) — the password is forgotten, so the next
  read asks for it again. Variables given to `:key use` stay in the environment
  (clear them explicitly with `:key unuse`). `:key autolock N` changes the
  delay for this session, `0` turns it off; `vault_idle_lock: 0` in settings.yml —
  for good.

  Examples: `:key init`, `:key add SSH_PROD prod ssh`, `:key cp SSH_PROD`
  then `> ssh …` (paste), or `:key exec SSH_PROD -- sshpass -e ssh user@host`
  (with sshpass installed).
